1) Dashboard Map

Overview

Current system posture: alert volume, throughput, component health, IoT counting source metadata, and provider availability.

Alerts

Alert history with severity, detector source, Kubernetes context, grouped incident counts, LLM outcome, and trace access.

IoT Mesh

Device/workload visibility and fleet status. Count quality is source-qualified (cluster telemetry vs fallback source). Protocol cards represent software emulators with real protocol shapes and synthetic state models unless a hardware path is explicitly used.

K8s Cluster

Operational status for IDS, database, detectors, and supporting workloads.

LLM Control

Provider health, failover chain, token/cost estimate metrics, routing strategy, and live provider diagnostics.

Automation

Governance mode, action counters, pending queue, and historical decisions with actor/status trail.

2) Status Glossary

LabelWhere It AppearsActual Meaning
Healthy / Operational Provider cards, component pills, service health views The live analysis or component path is working now. For LLMs, this means the provider has completed successful alert-analysis calls in the current process.
Degraded Provider tables, system status, IoT source-quality notices The system is still available, but a warning condition exists. For LLM providers, this usually means cooldown after a recent provider failure or a partial health state. For IoT metrics, it means telemetry is being derived from fallback sources rather than the full preferred path.
Cooldown Detailed provider cards in LLM Control The provider recently failed and is temporarily suppressed by the retry/circuit-breaker logic. It will retry automatically after the cooldown expires or after a manual reset.
Circuit open Detailed provider cards in LLM Control The provider crossed repeated-failure thresholds and the circuit breaker blocked additional traffic. This protects the IDS from repeatedly calling a failing or overloaded provider.
Analysis unverified Overview provider list The provider is configured, but this process has not yet recorded a successful alert-analysis call. Do not treat it as proven operational until a strict provider test or real alert analysis succeeds.
Auth failed / Unhealthy Provider cards, health views The configured provider or component is failing. Typical causes are invalid API keys, expired credentials, connectivity failures, or backend startup errors.
In-memory fallback Overview and health views The IDS API is still serving requests, but PostgreSQL is unavailable and persistence is temporarily degraded. Data created in this mode resets on restart unless the database reconnects.
Registered IoT Mesh device table The device exists in the logical registry, but there is no recent evidence that it is currently live. A registered row is inventory, not proof of active hardware.
Online / Healthy (device) IoT Mesh device table The device has recent heartbeat/telemetry or is backed by a currently running pod. This is the strongest dashboard evidence that the device is active now.

3) Tab-by-Tab Field Guide

Overview

  • Total Alerts / Critical Alerts: current recent alert totals from the IDS backend.
  • IoT Devices: hybrid inventory count using logical registry rows plus pod-backed workloads. Read the source-quality note under the number before making fleet-size claims.
  • Flood Suppression: cumulative rate-limiter throttling count since startup or last reset, not a hidden rolling minute.
  • Dedup + LLM Savings: real deduplicator savings shown only after duplicate-capable security alerts have been processed in the current process.
  • Recent Alerts: grouped into 5-minute incident buckets for readability. This reduces repeated Falco bursts that would otherwise drown out lower-volume Suricata rows.

Alerts

  • Search: filters by rule, summary, detector, or threat text.
  • Severity: normalized IDS severity on a 1-10 scale. The rule and summary text still come from the original detector or IDS pipeline.
  • Where: namespace, pod, and container context when available. Platform rows come from monitoring/security infrastructure rather than city service workloads.
  • Count: grouped-incident frequency within the collapse window, not a lifetime count.
  • View Full LLM Trace: audit viewer for prompts, parsed output, raw provider response, and metadata.

IoT Mesh

  • Source: distinguishes pod-backed devices from logical registry rows.
  • Last Seen: most recent heartbeat/telemetry or pod-derived activity timestamp used for device status classification.
  • Device / Pod IP: pod IP for pod-backed workloads, or the last registered device IP/metadata IP when available for external logical devices.
  • Important: a logical registry row without recent heartbeat and without IP should be treated as inventory only, not live hardware proof.

K8s Cluster

  • Shows live pod and service state for IDS API, detectors, database, and emulator workloads.
  • Use this tab to confirm whether a dashboard problem is really a cluster runtime problem.

LLM Control

  • Analysis: whether live alert-analysis calls are succeeding for that provider.
  • Billing endpoint: whether the provider credit/billing health path is reachable. This is separate from inference success.
  • Balance visibility: whether the provider/account actually exposes a usable balance value to the dashboard.
  • Provider Breakdown: DB-backed alert-analysis usage only. Manual probes and sanity tests do not increment these call totals.
  • Strict provider test: disables fallback during diagnostics so a provider either succeeds on its own or fails honestly.

Automation

  • Approved: total executed actions, combining auto-executed and manually approved actions.
  • Rejected: analyst rejections from the governance queue.
  • Pending: actions awaiting analyst review now.
  • Action history: authoritative trail for what governance decided and who approved or rejected it.

4) Automation Control (Governance)

ModeExecution BehaviorExpected Queue Behavior
manual LLM can recommend actions, but execution is blocked pending analyst approval. pending_approval increases for actionable events.
assisted High-confidence actions may execute automatically; medium-confidence actions are queued. Pending queue varies by confidence/policy thresholds.
autonomous Policy-approved actions execute automatically when thresholds are met. Benign alerts should normally produce no pending actions.

LLM Full Autonomy Profile: optional runtime profile that removes confidence gating in autonomous mode. Protected targets are still constrained by governance safety checks.

Interactive UI exposes only manual, assisted, and autonomous. Emergency/bypass capabilities are out-of-band and intentionally not UI-controllable.

5) How to Read "View Full LLM Trace"

  • Parsed output: normalized severity, threat type, confidence, and recommended actions.
  • System prompt: IDS policy/instruction context sent to provider.
  • User prompt: detector payload and normalization context.
  • Raw response: unmodified provider completion for auditability.
  • Metadata: provider, model, latency, trace source.

Analyzed · provider means a live provider call was made. Cached analysis means output was served from dedup/cache logic.

If a row reports missing inline trace, use the trace identifier and query /api/audit/trace/<trace_id>.

Provider diagnostics note: in LLM Control, enable Strict provider test to disable fallback during test calls. This verifies whether a specific provider actually succeeds, instead of silently failing over.

Provider card note: each provider card now separates Analysis, Billing endpoint, and Balance visibility. These are different checks. A provider can have a working analysis path while the billing endpoint is restricted or the balance is not exposed by that provider API.

Unverified analysis note: if a provider has no successful alert-analysis calls in the current process, the dashboard marks it as Analysis unverified even when the provider is configured. This avoids overstating readiness after restart.

Usage accounting note: the provider breakdown table is DB-backed and counts only alert-analysis calls that were executed as part of the IDS pipeline. Manual probes, sanity tests, and strict evaluation reanalysis with persist=false update provider health/diagnostics, but they do not increment the DB-backed alert-analysis usage counters shown in the provider breakdown table.

Success column note: a provider marked Hist means historical DB-backed usage exists, but runtime success counters were reset after restart, so the UI cannot compute a live success percentage for that same window.

Overview metrics note: `Dedup + LLM Savings` appears only after real duplicate-capable security alerts were seen by the deduplicator in the current process. `Flood Suppression` is cumulative since startup/reset, not a hidden rolling UI window.

Alert history note: repeated alerts are grouped into 5-minute incident buckets by detector, rule, severity, workload, and threat signature. This keeps repeated Falco/governance bursts readable and makes lower-volume Suricata rows easier to surface in the loaded history window.

IoT realism note: the strongest current emulator paths are ONVIF traffic camera, FHIR healthcare gateway, MQTT/SenML parking gateway, Modbus/OPC-UA environmental sensor, and DALI/TALQ street lighting. These are protocol-faithful software emulators, not physical devices. Parking MQTT, Modbus write, and DALI command paths now modify emulator state during live attack runs.

7) Troubleshooting

Automation panel shows unavailable/session expired

  • Sign in again to refresh token.
  • Check governance APIs directly with bearer token.
TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin"}' \
  http://localhost:30800/api/auth/login | jq -r '.access_token')

curl -s -H "Authorization: Bearer $TOKEN" http://localhost:30800/api/governance/status | jq
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:30800/api/governance/pending | jq

Database shows memory fallback

  • Check for restrictive network policies and DB connectivity.
  • Verify health endpoint and restart IDS API deployment if needed.
curl -s http://localhost:30800/health | jq '.components.database'
kubectl get networkpolicy -n smart-city
kubectl rollout restart deploy/ids-api -n smart-city

LLM provider shows Degraded, Cooldown, or Circuit open

  • Degraded: the provider is configured but temporarily limited or partially unhealthy.
  • Cooldown: a recent provider failure triggered temporary suppression; retry after the cooldown or use the retry/reset API.
  • Circuit open: repeated failures crossed the circuit-breaker threshold and traffic is blocked until recovery or reset.
  • Check the exact live reason in /api/llm/diagnostics before changing keys or billing settings.
curl -s http://localhost:30800/api/llm/diagnostics | jq .
curl -s http://localhost:30800/api/circuit-breaker/status | jq .

TOKEN=$(curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin"}' \
  http://localhost:30800/api/auth/login | jq -r '.access_token')

curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://localhost:30800/api/llm/retry-all | jq .
