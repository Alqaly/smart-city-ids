1. JWT AUTHENTICATION
   ✅ Token-based access control
   ✅ Automatic expiration (1 hour default)
   ✅ Cryptographically signed (HS256)
   ✅ Extracted claims: user ID, role, permissions
   
   Example:
   $ curl -X POST http://localhost:8000/api/auth/login \
     -d '{"username":"analyst","password":"password123"}'
   
   Response:
   {"access_token":"eyJ0eXAiOiJKV1QiLCJhbGc...","token_type":"bearer"}
   
   Use token:
   $ curl http://localhost:8000/api/alerts \
     -H "Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGc..."

2. ROLE-BASED ACCESS CONTROL (RBAC)
   ✅ 4 roles: Admin, Analyst, Monitor, Service
   ✅ Role-specific permissions
   ✅ Enforced at API endpoint level
   
   Role Matrix:
   • Admin:    Read/write/delete everything + manage users
   • Analyst:  Read/write alerts & analysis + execute automation
   • Monitor:  Read-only alerts & analysis + view dashboard
   • Service:  Write alerts only (Falco, Suricata forwarders)

3. DATA ENCRYPTION (Fernet)
   ✅ AES 128-bit encryption
   ✅ Encrypted fields: alert data, analysis, results
   ✅ Each record encrypted independently
   ✅ Supports future key rotation
   
   What's encrypted in DB:
   • Full alert JSON ({"output":"...", "rule":"...", ...})
   • LLM analysis results
   • Detailed threat analysis

4. AUDIT LOGGING
   ✅ Every action recorded (who, what, when, where)
   ✅ Success/failure status
   ✅ IP address and user agent
   ✅ Resource IDs and details in JSON
   
   Audit trail answers:
   • Who accessed this alert?
   • What did this user do?
   • When was this action taken?
   • Did it succeed or fail?

5. USER MANAGEMENT
   ✅ Create users with roles
   ✅ Password hashing (bcrypt)
   ✅ User activation/deactivation
   ✅ Email verification (future)
   
   Admin operations:
   • CREATE: CREATE new users
   • READ: View user profiles
   • UPDATE: Change roles, passwords
   • DELETE: Remove users (audit trail kept)

6. API KEY MANAGEMENT
   ✅ Service-to-service authentication
   ✅ API keys stored as hashes (not plaintext)
   ✅ Expiration dates
   ✅ Usage tracking
   
   Use case: Suricata forwarder
   • Assigned API key: "sk_live_abc123xyz..."
   • Uses key in header: "X-API-Key: sk_live_abc123xyz..."
   • No password needed (key is the credential)

  DATABASE SCHEMA (6 TABLES)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

users (user accounts)
  ├─ id, username, email
  ├─ hashed_password (bcrypt)
  ├─ role (admin|analyst|monitor|service)
  └─ is_active, is_verified, created_at, last_login

api_keys (service authentication)
  ├─ id, user_id (FK)
  ├─ key (hashed)
  ├─ name, description
  ├─ is_active, last_used, expires_at
  └─ created_at

alerts (security alerts - ENCRYPTED)
  ├─ id, alert_id (UUID)
  ├─ source (falco|suricata), rule, severity
  ├─ encrypted_alert_data (BYTEA) ← Full JSON encrypted
  ├─ encrypted_analysis (BYTEA) ← Analysis encrypted
  ├─ container_name, threat_type
  ├─ is_analyzed, actions_taken (JSON)
  └─ created_at, processed_at, created_by

analysis_results (LLM analysis - ENCRYPTED)
  ├─ id, alert_id (FK)
  ├─ model (groq/openai), encrypted_result (BYTEA)
  ├─ analysis_time_ms, confidence_score
  └─ analyzed_at

automation_actions (K8s automation record)
  ├─ id, alert_id (FK)
  ├─ action_type, target_resource, target_namespace
  ├─ status, error_message, execution_time_ms
  └─ created_at, completed_at, triggered_by

audit_logs (complete action trail)
  ├─ id, user_id (FK)
  ├─ action, resource_type, resource_id
  ├─ details (JSON), status, error_message
  ├─ ip_address, user_agent
  └─ created_at

Query examples:
  -- Who accessed this alert?
  SELECT * FROM audit_logs 
  WHERE resource_type='alert' AND resource_id='alert-12345';
  
  -- What did analyst1 do?
  SELECT * FROM audit_logs 
  WHERE user_id=(SELECT id FROM users WHERE username='analyst1')
  ORDER BY created_at DESC;
  
  -- Show failures in last hour
  SELECT * FROM audit_logs 
  WHERE status='failure' AND created_at > NOW() - INTERVAL '1 hour';
