# Academic Context: An Implementation-Level IIoT Emulation

This document provides the academic justification for the system's architecture, classifying it as an **implementation-level IIoT emulation** on Kubernetes. It is intended to defend the methodology against scrutiny in a Capstone or IEEE context.

---

### Task 1: System Classification

This system is an **implementation-level Industrial Internet of Things (IIoT) emulation on Kubernetes**.

It is **not a simulation**. A simulation models a system's behavior mathematically or abstractly, often omitting implementation details. This system does the opposite: it uses real, containerized services, real network protocols, and real security tools to create a high-fidelity, interactive environment that *emulates* the behavior and security characteristics of a simplified smart city.

#### Why Emulation is a Valid Methodology in Security Research

In cybersecurity and systems research, emulation is a widely accepted and powerful technique. It provides a crucial bridge between theoretical models and real-world deployments.

1.  **Behavioral Realism**: Emulation focuses on replicating the *actual behavior* of components. The Python services in this project execute real code, open real network sockets (HTTP, MQTT), and interact with a real filesystem and kernel. This is essential for evaluating security tools like Falco, which monitor kernel-level system calls—events that are impossible to generate from a purely mathematical simulation.

2.  **Implementation-Specific Vulnerabilities**: Many security flaws arise from specific implementation choices, library versions, or configurations, not abstract designs. By using real containers and services, this emulation exposes a realistic attack surface, including potential vulnerabilities in the Flask framework, container runtime, or network stack.

3.  **Toolchain Compatibility**: The system uses the exact same tools found in a production environment (Kubernetes, Docker, Prometheus, Grafana, Falco). This validates that the entire security and monitoring toolchain can correctly observe, interpret, and react to events generated by the emulated devices.

#### Comparison to Related Concepts

*   **Testbed**: This system can be considered a specialized form of a testbed. While a general-purpose testbed provides a configurable environment, our system is a *purpose-built* testbed designed specifically to emulate the security dynamics of an IIoT ecosystem.

*   **Cyber-Range**: It is a small-scale, private cyber-range. Cyber-ranges are interactive environments for cybersecurity training, testing, and research. This project provides a sandbox to launch attacks (e.g., `ddos_simulator.py`) and observe the defensive response of the integrated IDS and automation logic in real-time.

*   **Digital Twin**: It is a simplified, security-focused digital twin. A full digital twin aims to be a comprehensive virtual replica of a physical asset. Our system is a twin of the *cyber-physical control plane*, focusing on the data flows, network interactions, and security signals of the IoT infrastructure, rather than the physical processes (e.g., traffic flow dynamics) themselves.

### Task 2: Implementation Audit (Summary)

A detailed audit of the codebase reveals a solid foundation for emulation, with some areas needing refinement to enhance realism.

*   **`smart-city-services/`**: These are the most realistic components. They are standard Flask applications representing plausible IoT services (traffic, parking, healthcare).
    *   **Realism**: High. They produce real HTTP traffic and have a realistic, albeit intentionally vulnerable, security surface.
    *   **IDS Signal**: They generate legitimate web traffic logs and can trigger network-level IDS alerts (e.g., from Suricata) or application-level alerts if instrumented.

*   **`iot-simulator/`**: This is the weakest link in the current implementation. The code itself (`mqtt_device.py`) is realistic, capable of producing genuine MQTT traffic. However, the Kubernetes manifests (`iot-simulator.yaml`) deploy it as a generic, scaled "load generator." This is not emulation.
    *   **Realism**: Low (in deployment). Replicas are not devices. The "burst" and "medium" labels are arbitrary and not tied to specific device behaviors.
    *   **Refactoring Action**: This directory will be repurposed. The generic `iot-simulator.yaml` has been removed and will be replaced with specific manifests that use the `mqtt_device.py` container to emulate distinct device classes.

*   **`services/`**: This contains the core IDS logic.
    *   **`ids-api`**: Realistic. It's a FastAPI application that receives real JSON alerts, makes real API calls to an LLM, and uses a real Kubernetes client to perform actions. Its behavior is entirely determined by the data it receives.
    *   **`forwarders/`**: Realistic. These services act as adapters, consuming output from tools like Falco and forwarding it over the network, a common pattern in security architectures.

---

This audit confirms the need to refactor the "simulation" aspect into a structured "emulation" model, which will be addressed in the next steps.
